# Migration/version-control tích hợp — xong (2026-09-23)

Gap #4 trong đợt so sánh DataGrip/DBeaver/Studio3T (`docs/roadmap.md`, Tier 5) — mục cuối cùng, roadmap ghi rõ "chưa rõ hình dạng, cần hỏi lại phạm vi". Chốt qua `AskUserQuestion` trước khi code (4 câu): **file migration kiểu Flyway/Alembic** (không phải chỉ log DDL đã chạy), track đã chạy bằng **bảng trong chính DB** (không phải file local), **độc lập** với table designer (không tự sinh migration từ `a`/`x`/`R`/`n`), **chỉ Postgres** ở v1 — khớp lý do table designer đã chọn Postgres.

**Nơi file sống**: `~/.config/tradar/migrations/<tên connection>/` (`storage::default_migrations_dir`, tên sanitize để không thoát khỏi thư mục) — mới, khác `default_queries_dir()` ở chỗ theo từng connection chứ không dùng chung, vì một bộ migration gắn chặt với một database cụ thể. Không thêm field mới vào `SavedConnection`/`connections.toml` — thư mục suy ra thẳng từ tên connection, không cần user cấu hình gì thêm.

**Quy ước file**: `<số>_<mô tả>.sql` (vd `001_create_users.sql`), số phải toàn chữ số, sort theo thứ tự chữ (nên cần zero-pad nhất quán — đúng cái bẫy Flyway thật cũng có). File không khớp quy ước bị bỏ qua âm thầm (không lỗi cả panel) — một README hay file backup trong thư mục không chặn migration thật chạy.

**Bảng track**: `_tradar_migrations (version TEXT PRIMARY KEY, name TEXT NOT NULL, applied_at TIMESTAMPTZ NOT NULL DEFAULT now())`, tự `CREATE TABLE IF NOT EXISTS` mỗi lần mở panel — gộp chung với câu `SELECT version` trong cùng một `submit_all` để lần đầu tiên (bảng chưa tồn tại) không bao giờ báo lỗi "relation does not exist".

**Quyết định kiến trúc quan trọng nhất — không cần hạ tầng engine mới**: `QueryEngine::submit_all`/`submit_query` (đã có sẵn cho row-edit/table-designer) đã đủ cho toàn bộ luồng chạy migration — mỗi file được gói thành `["BEGIN", ...statement của file (qua engine.split_statements), INSERT vào _tradar_migrations, "COMMIT"]` rồi gọi `submit_all` y hệt cách `run_table_ddl` gọi. Panel tự điều phối chạy tuần tự từng file bằng cách phản ứng với outcome mỗi tick (`QueryScreenComponent::tick()`), không phải một cơ chế batch mới trong `QueryEngine`. Nhờ vậy **không cần** `QueryDriver` method mới để build SQL (khác `table_ddl`) — BEGIN/COMMIT/INSERT là SQL ANSI thường, không có gì riêng theo dialect. Chỉ cần một cờ khả năng đơn giản: `QueryDriver::supports_migrations() -> bool` (mặc định `false`, chỉ Postgres trả `true`) — vì không có SQL nào cần build khác nhau theo driver ở đây, `Option<String>` kiểu `table_ddl` không hợp, boolean là đủ.

**An toàn khi outcome đến sau khi panel đã đóng**: `tick()` định tuyến outcome dựa trên `self.migrations_query` (field riêng, tồn tại độc lập với panel có đang hiển thị hay không), **không** dựa trên `self.migrations.is_some()`. Trong khi một file đang chạy (`Stage::Running`), panel cố tình bỏ qua mọi phím — không có cách nào "huỷ" một submission đã gửi đi, nên thay vì cố gắng xử lý outcome mồ côi, đơn giản là không cho đóng panel giữa chừng.

**Lỗi giữa chừng**: 1 file lỗi → dừng chạy tiếp, tự gửi `ROLLBACK` (fire-and-forget qua `MigrationsQuery::Rollback`, outcome của nó không làm gì thêm vì lỗi đã hiển thị rồi), các file trước đó **giữ nguyên đã commit** (không rollback ngược) — đúng ngữ nghĩa Flyway thật (`migrate` dừng ở statement lỗi, không lùi lại những gì đã áp dụng).

**Kích hoạt**: `F1` trong `Context::QueryScreen` (F2/F3/F4/F5/F6 đã dùng hết, F1 còn trống) — panel connection-scoped, không phải hành động nhắm vào 1 bảng/cột như table designer nên không đặt trong navigator.

**Chưa refresh navigator sau khi chạy** — cùng giới hạn đã ghi nhận ở table designer (`docs/backlog/table-designer.md`): `list_schema()` chỉ fetch một lần lúc connect.
