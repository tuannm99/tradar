# Backlog

Tracks the DB-IDE feature roadmap and known issues deferred out of past work. This is the durable record of project status and design rationale — `docs/architecture.md` covers system design, this file covers what's done/in-progress/not-started and why. Update it directly whenever a sub-project starts/finishes or a new issue is deferred.

## Sub-project roadmap

Decomposed from a single broader request ("DataGrip/DBeaver-style DB IDE features: vim keymap, save/load, sessions, UI polish"). Each item below tracks its own design/status inline rather than through separate spec/plan documents.

1. **Component Architecture migration** — done, merged to `master` (2026-08-02/03). Replaced the flat `App`/`tui` design with `src/action.rs` (`Action` enum + `Component` trait) + `src/components/`. Foundation for the items below.
2. **Vim keybindings throughout the TUI** — done, not yet committed. Scope corrected 2026-08-07: this is *not* just the query editor. The real requirement is vim-style keybindings across every panel — connection list, query editor, and results — with the results panel additionally supporting easy copy/yank of one or multiple records. Breakdown:
   - **Query editor** (using `edtui`) — done, merged to `master` (commit `1255e54`, includes the `Cargo.toml` `ratatui` 0.29 → `0.30` bump). `edtui::EditorState` lives as a plain field on `QueryEditorComponent` (owned by `QueryScreenComponent`, the component that hosts it), not baked into `Action`/`Component`; `Esc` is context-sensitive (Insert/Visual/Search→Normal mode inside the editor first, only bubbling to `BackToPicker` once already in Normal mode) — this touches the same `handle_key_event` arm ordering that the schema-sidebar, Component-migration, and this work's own final reviews all had to fight to keep correct; regression tests for it exist in `src/components/query_screen.rs`. SQL syntax highlighting was considered (edtui bundles a `syntect`-based `syntax-highlighting` feature) and deliberately left off — heavy dependency, not yet scoped.
   - **Connection list / schema sidebar navigation** — done, not yet committed. Both `ConnectionPickerComponent` and `SchemaSidebarComponent` now support `j`/`k`/arrow keys, `gg`/`G` (jump to top/bottom), and `Ctrl+d`/`Ctrl+u` (half-page scroll, sized off each component's own last-rendered visible row count, tracked via a `visible_height` field set in `draw()`). `gg` detection uses a `pending_g: bool` field consumed via `std::mem::take` at the top of `handle_key_event`, so any other key cancels a lone `g` instead of leaving it stuck. For the schema sidebar (not a `Component` itself), the new bindings are wired the same way as the existing `j`/`k`: `QueryScreenComponent`'s sidebar-focus key arm returns new `Action::SchemaMoveTop`/`SchemaMoveBottom`/`SchemaHalfPageUp`/`SchemaHalfPageDown` variants, handled in `update()`. When the editor has focus instead, `g`/`G` fall through to `edtui`'s own vim handling untouched.
   - **Results panel vim navigation + copy** — done, not yet committed. `ResultsComponent` now tracks a `selected: usize` item index (a row for `QueryResult::Table`, a document for `QueryResult::Documents`), rendered via a `List`/`ListState` (replacing the old flat `Paragraph`) with the same `j`/`k`/`gg`/`G`/`Ctrl+d`/`Ctrl+u` navigation as the schema sidebar. `Focus` gained a third variant, `Results`; `Tab` now cycles `Editor → Results → Sidebar → Editor`. Copy mechanism: `y` yanks the selected row (tab-separated) or document (pretty-printed JSON) via an OSC52 escape sequence (`Action::Yank { text }`, handled in `main.rs` like `ExportCurl` — no clipboard crate needed, works through SSH/tmux on terminals that support OSC52). Verified end-to-end in a real terminal (tmux): connect, run a multi-row query, `Tab` into Results, `j`/`gg`/`G` move the highlight correctly, `y` doesn't crash.
3. **Save/load query to file** — not started.
4. **Sessions/workspace state** — not started; scope not yet clarified (query history? multiple simultaneous tabs/connections? state persisted across runs?). Needs its own brainstorming pass to scope before designing.
5. **General UI polish** — not started; intentionally last, since it needs the other features to have real shape first.
6. **Pluggable connector architecture migration** — not started. Target shape (`Connector → Session → Screen`, Cargo workspace split so non-query-shaped systems like Kafka/RabbitMQ/Kubernetes can be added without touching core) is fully specified in `docs/architecture.md`'s "Target architecture: pluggable connectors" section. Cross-cutting: touches all five existing drivers, `RootComponent`, `main.rs`, and `storage`; meant to be done incrementally, not as one large change.

## Known issues (deferred, not blocking)

From the Component Architecture migration's task reviews and final whole-branch review (recorded here so it isn't lost):

- ~~**Postgres connect hangs 30s with no feedback against an unreachable host.**~~ Fixed. `PostgresDriver::connect()` used `PgPool::connect()`, which inherits sqlx's default 30s `acquire_timeout` — against a refused connection this made the TUI look completely unresponsive (no error, no indication anything was happening) for a full 30 seconds before `PoolTimedOut`. Now uses `PgPoolOptions::new().acquire_timeout(Duration::from_secs(5)).connect(...)`. Regression test: `drivers::postgres::tests::connect_fails_quickly_against_an_unreachable_host` in `src/drivers/postgres/mod.rs`, which needs no Docker (connects to port 1, always refused) and bounds the wait with `tokio::time::timeout`.
- ~~**Connect-vs-connect race.**~~ Fixed. `ConnectionPickerComponent` now owns a `connect_epoch: u64` counter, bumped and stamped onto `Action::ConnectRequested` on every connect attempt; `main.rs`'s `spawn_connect` threads that epoch through to the `Connected`/`ConnectFailed` it sends back. `RootComponent::update` drops any `Connected`/`ConnectFailed` whose epoch doesn't match `connection_picker.connect_epoch`, so a reply from a superseded connect attempt can no longer silently switch the UI back. Same pattern as the existing query-epoch mechanism in `QueryScreenComponent`. Covered by `components::tests::a_stale_connected_from_a_superseded_connect_attempt_is_ignored` and `...a_stale_connect_failed_from_a_superseded_connect_attempt_is_ignored` in `src/components/mod.rs`.
- `ConnectionPickerComponent.last_error` is only ever set, never cleared on a successful retry (`src/components/connection_picker.rs`). Low priority — cosmetic (a stale error sits behind the query screen until the next failed connect attempt).
- No test exercises `Ctrl+Y` (curl export) while the schema sidebar has keyboard focus in `QueryScreenComponent` — only `F5`/`Ctrl+Enter` are tested against the sidebar-focus guard. Same protection mechanism (checked before the guard in match-arm order), so low risk, but worth adding for completeness.
- `main.rs`'s `event::poll(Duration::from_millis(50))` is a synchronous call that can block its tokio worker thread up to 50ms per idle tick. Bounded and not correctness-affecting on the default multi-threaded runtime, but `crossterm::event::EventStream` + `tokio::select!` would be the non-blocking alternative if this ever becomes a real problem.
- Stylistic inconsistency: `ResultsComponent`, `QueryEditorComponent`, and `SchemaSidebarComponent` each implement `Default`/`new()` slightly differently (some derive `Default` and hand-write an identical `new()`, one hand-writes `Default` delegating to `new()`). Pick one convention and apply it across all three next time one of those files is touched.
