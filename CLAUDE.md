## Project state

The repo is a Cargo workspace (sixteen crates: `tradar-core`, `tradar-connector-spi` (the `Connector`/`Session` trait contracts every connector implements — named `-spi`, not `-api`, specifically so it doesn't read like just another item in the `tradar-connector-<name>` family below), `tradar-query-workbench`, twelve connector crates — each named `tradar-connector-<name>`, living directly under `crates/` rather than nested under a `connectors/` subdirectory — and the `tradar-app` binary; see `docs/architecture.md`'s "Triển khai hiện tại" section for the exact layout and why it's split this way). `cargo run`/`cargo build`/`cargo test` all work with no `-p` flag (`default-members = ["crates/tradar-app"]`; the binary is still named `tradar`). It's a runnable walking skeleton: `tradar` connects to a real PostgreSQL, MySQL/MariaDB, SQLite, MongoDB, Elasticsearch, Redis, Cassandra, ClickHouse, RabbitMQ, Kafka instance, an arbitrary HTTP endpoint, or a raw TCP socket. Eight of those twelve go through `QueryDriver` implementations, running queries through `query_engine` and rendering a connection picker + query/results screen — ClickHouse (added 2026-09-29, `docs/backlog/clickhouse-connector-2026-09-29.md`) is the only one of the eight not built on `sqlx`/a native client: it speaks real SQL (shares `SQL_KEYWORDS`/`split_sql_statements` with Postgres/MySQL/SQLite) but talks to ClickHouse's own HTTP interface via `reqwest`, appending `FORMAT JSON` to row-returning statements so the response carries both column names and types the way `QueryResult::Table` needs; it has no row-edit (`edit_sql`/`edit_source` unimplemented) since ClickHouse has no ANSI `UPDATE`/`DELETE`, only asynchronous `ALTER TABLE ... UPDATE/DELETE` mutations. MySQL/MariaDB (added 2026-10-01, `docs/backlog/mysql-connector-2026-10-01.md`) is one driver for both (MariaDB speaks the same wire protocol sqlx's `mysql` feature targets): built on `sqlx` like Postgres/SQLite, reading `information_schema` for schema/FK/primary-key info (simpler than Postgres's joins — MySQL's `information_schema.columns.column_key`/`key_column_usage.referenced_table_name` carry PK/FK info directly, no extra join needed) and recovering an approximate syntax-error position the same way SQLite does (`near 'X' at line N` in MySQL's own message, vs. SQLite's `near "X": syntax error`) since neither reports one the way Postgres's wire protocol does; it has no table designer or migration tracking (both still Postgres-only). Kafka, RabbitMQ, HTTP, and Socket have no query language, so they implement `Session`/`Connector` directly (`tradar-connector-spi`) and each ships its own bespoke `Screen` (`KafkaScreen`/`RabbitScreen`/`HttpScreen`/`SocketScreen`, in `crates/tradar-connector-kafka|rabbitmq|http|socket/src/screen.rs`) instead of reusing `QueryScreenComponent` — Kafka has two modes toggled by `F2` (`Context::Kafka`'s `KafkaToggleMode`): Topics (tails a topic in real time -- bounded per-tick channel drain, `rdkafka` -- and publishes) and Groups (added 2026-10-01, `docs/backlog/kafka-groups-mode-2026-10-01.md`: per-partition consumer lag for a selected group, computed by a throwaway consumer configured with that `group.id` -- never subscribed/assigned, so it never joins the group's real membership -- calling `committed_offsets()`/`fetch_watermarks()`, read-only, no seek/reset); RabbitMQ browses queues/exchanges and peeks/publishes messages over the Management HTTP API (`reqwest`, no AMQP client); HTTP is a Postman-style request builder (method/URL/headers/body + response pane, `reqwest`); Socket (added 2026-09-29, `docs/backlog/socket-connector-2026-09-29.md`) is raw TCP, netcat-style, over `tokio::net::TcpStream` directly (no library) -- no sidebar, one scrolling transcript panel plus one always-typable input line, which is why its `Context::Socket` keymap binds scrolling to arrow keys/`ctrl-d`/`ctrl-u` and reconnect to `ctrl-r` rather than the `j`/`k`/`gg`/`G`/`r` every other list/sidebar in the app uses -- a bare letter there would be swallowed as typed text instead of a command, since (unlike Kafka/RabbitMQ's sidebar-then-detail layout) there's no un-typable pane to bind them to. All of this is driven by the `Component`/`Action` architecture (`RootComponent` in `tradar-app` holding `Vec<Tab>`, each independently on the picker or an active connector screen, wired together via the `mpsc` event loop in `main.rs`). Connections are added/edited/deleted from the picker itself (`a`/`e`/`d`, form in `crates/tradar-app/src/components/connection_form.rs`), persisted to a TOML file (`crates/tradar-core/src/storage/mod.rs`) that can still be hand-edited. Schema browsing is a **navigator** panel in the app shell (`crates/tradar-app/src/components/navigator.rs`, `Ctrl+B`): a `connection → table → column` tree over *every* saved connection, not just the current tab's — opening an unconnected one connects it into its own tab, and `Enter` on a name inserts it into that connection's own editor. Screens feed it through `Component::outline()`/`insert_text()` (same opaque-string contract as `restore_state`), so the shell never learns what a table is; `OutlineEntry::is_object` (not `depth`, which varies now) marks which entries are real objects a CRUD snippet can target versus a grouping folder. PostgreSQL/Cassandra/MongoDB insert one or two extra levels between connection and table — `SchemaInfo::schema` (Postgres schema, Cassandra keyspace, MongoDB database) and, Postgres only, `SchemaInfo::object_kind` (table/view/function/procedure) — built by `flatten_outline` in `crates/tradar-query-workbench/src/components/query_screen.rs`, which skips a grouping level entirely for a driver that never sets the field (SQLite/Elasticsearch/Redis stay exactly the flat two-level tree). MongoDB's schema is inferred, not declared: `list_schema` samples one document per collection and flattens it into `parent.child` columns, `_id` marked as the key; it now lists every database on the server, not just the one current at connect time. `ColumnInfo::indexed` similarly comes only from Mongo (a concurrent `list_indexes()` per collection, matched back to `flatten_document`'s dotted field names — `_id`'s own implicit index excluded since `primary_key` already covers it), surfaced in the navigator's column detail as an `idx` marker alongside `pk`; Postgres/MySQL/SQLite/Cassandra/ClickHouse's own index concepts aren't reported through this field yet, only Mongo's. `ColumnInfo::foreign_key` (Postgres/MySQL/SQLite only — Cassandra has no FK concept, Mongo/Elasticsearch/Redis stay schemaless) drives two features that share it: context-aware completion in the query editor (`.` after a `FROM`/`JOIN` alias offers only that table's columns, a table name typed right after `JOIN` ranks one with an FK to/from a table already in the query first — `query_driver::completion_context`) and an ERD overlay (`F4`, `crates/tradar-query-workbench/src/components/erd.rs`) that renders one picked table's immediate FK neighborhood as a box-drawing diagram in the terminal, not the whole schema at once. `completion_context` also recognizes Mongo's own shell shape apart from SQL's `alias.column`: a field typed inside a `db.<collection>.find({...` call's arguments scopes to that collection's own fields (`mongo_collection_in_scope`, found by scanning back for the call's `db.<collection>.<method>` token at a shallower paren depth than the cursor), and typing the method name itself (`db.orders.f`, not yet past an opening paren) gets its own `CompletionContext::MongoMethod` — narrowed to method-name keywords only, not just re-ranked, since a collection or field name is never a legal completion there (without this, a field/collection sharing the same prefix as `find`/`aggregate`/... would otherwise rank above it, `CandidateKind::Table`/`Column` outranking `Keyword` in the flat list every other context falls back to). Every open connection self-checks liveness in the background (`QueryDriver::ping`, every 15s via `QueryEngine::tick`) and surfaces a drop through `Component::connection_alive()` as a red "disconnected" badge in the query editor and a marker in the navigator, without waiting for a query to fail first. The results grid is editable: cell cursor (`h`/`l`), row numbers, and `Enter`/`d` to change or delete the selected row by generating the driver's own edit statement (via `QueryDriver::edit_source`/`edit_sql`/`edit_key_columns`), showing it, and running it only after a `y` — Postgres/MySQL/SQLite (`UPDATE`/`DELETE`, keyed by the connection's own schema-declared primary key) from the start; Mongo (`updateOne`/`deleteOne` on a plain `find()` result, keyed by `_id`) and Elasticsearch (`_update`/`DELETE _doc` on a single-index `_search` result, keyed by `_id`) added 2026-09-07 (`docs/backlog/mongo-es-row-edit.md`) — both infer a JSON-typed value from the text typed into the edit prompt rather than always quoting as a string the way SQL's auto-coercion lets `build_sql_edit` get away with, and Elasticsearch's `execute()` was changed the same day to unwrap a `_search` response's `hits.hits` into one `Documents` entry per hit (each carrying its own `_id`) instead of the whole response staying one opaque document, which is what makes a hit addressable at all — `edit_key_columns` (a new `QueryDriver` method, `None` default falling back to schema-declared `primary_key` columns) exists because Elasticsearch's `_id` is metadata no index mapping ever declares, unlike Mongo's `_id` (a real, schema-visible field `list_schema` already marks `primary_key: true`). The query editor is a hand-rolled text editor (`crates/tradar-query-workbench/src/components/query_editor.rs`, no longer backed by `edtui`) with tree-sitter SQL syntax highlighting on Postgres/MySQL/SQLite/ClickHouse/Cassandra connections, bracket/quote auto-close+skip-over, and its own undo/redo. It supports two editing modes, chosen once at startup via `[editor]` `vim-mode` in `~/.config/tradar/config.toml` (`tradar_core::config::vim_mode()`, default `false`, no runtime toggle — see `QueryEditorComponent::new()`'s doc comment for why the setting is applied by `QueryEngine::build_screen` rather than read inside `new()` itself): vim-modal (`u`/`U` — `U` instead of vim's `ctrl-r`, which query-screen already claims for history and intercepts before the editor ever sees it) or, by default, plain non-modal editing (`Ctrl+Z`/`Ctrl+J` undo/redo, since `u`/`U` only exist in vim's Normal mode). Vim-modal Normal mode's own operation set was extended 2026-10-02 (`docs/backlog/vim-operations-gap-2026-10-02.md`): word motions `w`/`b`/`e` (`QueryEditorComponent::move_word_forward`/`move_word_backward`/`move_word_end`, small-word semantics — `is_word_char` runs vs. punctuation runs vs. whitespace, a line break always its own boundary even between two same-class runs); a general operator-pending mechanism (`d`/`c`/`y` now single-key `Context::VimNormal` bindings, `Command::EditorOperator*`, replacing the old literal `"dd"`/`"yy"` two-key bindings — the keymap itself has no "operator pending" notion, so `QueryEditorComponent::pending_operator`/`complete_operator`/`operator_motion` track it) supporting the doubled operator (`dd`/`cc`/`yy`, whole current line) and operator+motion for `w`/`b`/`e`/`0`/`$` only (`dw`, `cb`, `y$`, computing the range by running the motion and reading where it landed, reusing Visual mode's own `delete_selection`/`yank_selection` against a synthetic `visual_anchor` rather than a real `v`/`V` session) plus `D`/`C`/`Y` as direct `$`-motion shorthands; text objects `iw`/`aw` (`word_text_object`, reusing `i`/`a`'s own `EditorEnterInsert`/`EditorAppend` commands as the scope signal rather than adding dedicated ones) composing with the same three operators (`diw`, `ciw`, `yaw`); `J` (join, collapsing the join point to one space, none if either side is empty), `~` (toggle case, moves right), `>>`/`<<` (indent/dedent by a fixed `INDENT_WIDTH`); and `.` (`Command::EditorRepeatLast`, `QueryEditorComponent::last_action`/`repeat_last`) replaying the last Delete/Yank-flavored action (never a Change one — those enter Insert, and capturing/replaying an entire typed session is out of scope) at the cursor's current position. Deliberately out of scope, documented in the same backlog entry: `h`/`l` as operator motions (without count support they'd always be exactly one character, already `x`/`X`), linewise operator-motion ranges (`dj`, `dG` — `dd`/`cc`/`yy` already cover "the current line"), and bracket/quote text objects (`i(`, `a"`). The same audit also found and fixed a handful of smaller vim-motion inconsistencies elsewhere in the app, same backlog entry: the "open query" file picker (`crates/tradar-query-workbench/src/components/file_picker.rs`) now takes `Ctrl-d`/`Ctrl-u` as half-page jumps (it already special-cased `Down`/`Up` around its own always-on-filter design — unlike `j`/`k`/`gg`/`G`, which stay plain typing there, `Ctrl-d`/`Ctrl-u` are control chords never typed into a filename, so there was no reason they were missing); the ERD overlay's (`crates/tradar-query-workbench/src/components/erd.rs`) `Ctrl-d`/`Ctrl-u` were a real bug, not just a gap — `ErdState::Viewing` had no `visible_height` field, so `vim_list::apply` was always called with a hardcoded `1`, making them silently degrade to single-line `j`/`k`-equivalent movement; and Kafka's Groups-mode lag table plus RabbitMQ's messages/bindings tables (`crates/tradar-connector-kafka|rabbitmq/src/screen.rs`) gained a `Focus` enum (`Sidebar`/`Detail`, toggled by `tab`/`Command::CycleFocus`, same command/key as `query_screen.rs`'s own editor↔results toggle) so `j`/`k`/`gg`/`G`/`Ctrl-d`/`Ctrl-u` can reach a row past the first screen, which neither detail table could do at all before (Kafka's Topics-mode message table keeps its own separate pause/follow model instead, `space`, and doesn't use `Focus`). Keys are resolved through `tradar-core`'s `keymap` module (per-`Context` command lookup, remappable from `~/.config/tradar/config.toml`) rather than matched inline in components, colors come from `tradar-core`'s `theme` module, and shared widgets (bordered panel, selection style, status hint bar, `?` help overlay) live in `tradar-core`'s `ui` module — components must use these rather than hardcoding a `KeyCode`, a `Color`, or their own `Block`. Multiple tabs/connections can be open at once (`Ctrl+T`/`Ctrl+W`/`Ctrl+Left`/`Ctrl+Right`), and the app remembers which tabs were connected across restarts. Results can be exported to CSV/JSON (`crates/tradar-query-workbench/src/export.rs`, `Ctrl+E`, gated by `Capability::Export` — declared by the SQLite, Postgres, MySQL, Cassandra, and Elasticsearch drivers), separate from Elasticsearch's own curl-export (`QueryDriver::export_curl`, `Ctrl+Y`/`Ctrl+G`). SQL errors get a `psql`-style `LINE N: ... ^` marker on Postgres, MySQL, SQLite, ClickHouse, and Cassandra, sharing one `query_driver::line_and_caret` (connector crates can't depend on each other): Postgres has a real reported character position from the wire protocol (`format_pg_error`); none of the other four report one, so each instead recovers an approximate position from a token its own error message quotes — `tradar-connector-sqlite`'s `format_sqlite_error`/`near_token_marker` from `near "X": syntax error`, `tradar-connector-mysql`'s own `format_mysql_error`/`near_token_marker` from `... right syntax to use near 'X' at line N`, `tradar-connector-clickhouse`'s `format_clickhouse_error`/`clickhouse_error_marker` from `failed at position N (<token>)` (added 2026-10-02, `docs/backlog/connector-ux-gaps-2026-10-02.md` — the numeric position itself is never trusted since its indexing base couldn't be verified against a live server, only the quoted token's own byte offset in the original query text), `tradar-connector-cassandra`'s `format_cassandra_error`/`cassandra_error_marker` from the ANTLR-style single-quoted token in scylla's own `DbError` reason string (e.g. `mismatched input 'FRO' expecting K_FROM`, same day). Elasticsearch's console validates the JSON body locally (`validate_json_body`) before ever sending the request, so a malformed body never reaches the cluster and the error points at the parse mistake itself rather than whatever Elasticsearch would have said about an unparseable request — accepting NDJSON (one JSON value per line, no commas) as well as a single JSON value, since `_bulk`/`_msearch` require that shape and an earlier version of this check rejected it outright as "trailing characters" after the first object. `execute()` also checks the response's HTTP status now (`handle_response`, a free function so the status-handling logic is testable without a real cluster) — a non-2xx response used to come back as an ordinary `QueryResult::Documents`, the error body rendering in the results pane as if it were data; now it's an `Err` carrying the pretty-printed error body, same as every other driver's failures. Sorting (`s`/`Command::SortColumn`) is a no-op in a `Documents` result's raw JSON view (`ResultsComponent::sort_by_column` checks `columns().is_empty()` first) — the JSON branch of `compute_visible_items` never reads `self.sort` at all, so setting it there used to look like nothing happened, only to "surprise-apply" once the view was toggled to the flattened table. MongoDB's own `split_statements` (what `Ctrl+Enter`/`Ctrl+A` use to find statement boundaries) now mirrors Elasticsearch's `starts_request`/`split_statements` pair instead of treating every line as its own statement: a line starting a new `db.<collection>.<method>`/`use`/`show dbs` call (`starts_mongo_statement`) starts a new statement, anything else extends the one above it — so a call written across several lines, the normal mongosh/Compass style, merges into one statement instead of each line failing to parse independently. MongoDB's CRUD-snippet generator (`crud_snippet`) no longer quotes a dotted field path (`address.city`, from `flatten_document` sampling a nested document) as a single flat key for `insertOne` — `nested_insert_literal` builds the real nested object (`{address: {city: <value>}}`) instead, since unlike `updateOne`'s `$set`/`deleteOne`'s filter (where Mongo itself reads a dotted key as a path expression, so `object_literal`'s flat quoting stays correct there), `insertOne`'s document literal has no such convention — a flat `"address.city"` key there would create one field literally named that, not a nested one. The connection form (`crates/tradar-app/src/components/connection_form.rs`) shows a one-line example `target` for the selected driver (`target_hint`, e.g. `postgres://user:password@localhost:5432/mydb`) under the Target field, and a failed connect's error (`main.rs::spawn_connect`) appends the same hint — a `sqlx`/`mongodb` error is about what went wrong reaching the server, not about what a valid target looks like, and neither the picker nor the underlying library's error previously said so. The full architecture — current implementation and the target pluggable-connector design it's migrating to — lives in `docs/architecture.md`; read it before adding new modules. A handful of small UI/UX gaps across the connectors not covered by `docs/backlog/sql-es-mongo-ux-2026-09-30.md` were closed 2026-10-02 (`docs/backlog/connector-ux-gaps-2026-10-02.md`): Redis's browse-sidebar key list and HTTP's saved-request picker each gained their own `/` filter bar (same live-filter/`Esc`-clears/`Enter`-keeps pattern as the navigator and Kafka/RabbitMQ sidebars — Redis's is bound in `Context::Browse`, which previously had no `/` binding in its resolution chain at all), and Kafka/RabbitMQ's sidebars plus Socket's transcript gained mouse support (click-to-select and double-click-to-open on the sidebar list, scroll-wheel to move the selection/scroll the transcript) alongside the keyboard-only interaction they had before.

Open/unscoped roadmap items live in `docs/roadmap.md`; finished sub-project history (one file per sub-project, what `docs/backlog.md` used to be before it grew past 450 lines) lives in `docs/backlog/`.

## What Tradar is

A terminal-first database exploration and query tool (TUI), in the spirit of LazyGit or k9s but for databases. It gives a unified, keyboard-driven interface for querying, browsing, analyzing, and managing different databases without switching between multiple native CLI clients — while still preserving each database's native query language (SQL for SQL databases, Mongo Shell JS for MongoDB, Query DSL for Elasticsearch) rather than inventing a custom query language.

v1 target databases: PostgreSQL, SQLite, MongoDB, Elasticsearch, Redis, Cassandra, Kafka, RabbitMQ (all eight implemented). Post-v1 database extension: MySQL/MariaDB (implemented 2026-10-01, one driver for both via `sqlx`'s `mysql` feature — see the note in "Project state" above), ClickHouse (implemented 2026-09-29, over its own HTTP interface rather than `sqlx` — no row-edit, see the note in "Project state" above). Post-v1 extension (not databases, same connector architecture): HTTP (implemented), Socket (raw TCP, implemented 2026-09-29 — see the note in "Project state" above); gRPC is designed in `docs/architecture.md` but not yet built — see `docs/roadmap.md`.

## Commands

This is a Rust project built with Cargo (edition 2024).

- Build: `cargo build`
- Run: `cargo run`
- Test: `cargo test` (run a single test: `cargo test <test_name>`)
- Lint: `cargo clippy`
- Format: `cargo fmt`
- Check without building: `cargo check`

`tradar-app`'s own connector dependencies are each behind a Cargo feature named after `ConnectorDescriptor::id` (`postgres`, `sqlite`, `mongo`, `elasticsearch`, `redis`, `cassandra`, `clickhouse`, `rabbitmq`, `kafka`, `http`, `socket`), `default = ["full"]` (all eleven) so a plain `cargo build`/`cargo run` is unchanged. Build a binary with only the connectors you actually want via `cargo build -p tradar-app --no-default-features --features mongo,elasticsearch` (or `make build-slim FEATURES=mongo,elasticsearch`) — this skips every other connector's own dependencies entirely, most usefully `kafka`'s (`rdkafka`, which needs `cmake`/`gcc`/`libcurl-dev` to build `librdkafka` from vendored source).

Ten of the twelve connectors' tests (Postgres, MySQL, Redis, Mongo, Elasticsearch, Cassandra, ClickHouse, RabbitMQ, Kafka, HTTP — everything but SQLite/Socket) spin up a real backend via `testcontainers`/`testcontainers-modules`, which requires a working Docker daemon. If Docker isn't available, run `make test-unit` (equivalently `cargo test --workspace --exclude tradar-connector-postgres --exclude tradar-connector-mysql --exclude tradar-connector-redis --exclude tradar-connector-mongo --exclude tradar-connector-elasticsearch --exclude tradar-connector-cassandra --exclude tradar-connector-clickhouse --exclude tradar-connector-rabbitmq --exclude tradar-connector-kafka --exclude tradar-connector-http --exclude tradar-app`, plus a second `cargo test -p tradar-app --no-default-features --features postgres,mysql,sqlite,mongo,elasticsearch,redis,cassandra,clickhouse,rabbitmq,http,socket` for `tradar-app` itself — split out so building it doesn't pull in `kafka`'s native toolchain requirement even though `tradar-connector-kafka` itself is excluded, see "Cargo feature flags" under "Registry" in `docs/architecture.md`) to exercise everything else; `make test-docker` runs just the Docker-dependent ones. Most cargo invocations need `--workspace` to cover every crate (e.g. `cargo clippy --all-targets --workspace -- -D warnings`).

## Architecture

See `docs/architecture.md` for the full module layout and the `QueryDriver`/`Connector`/`Session` trait contracts. The rule that matters most for any change: code in each connector crate (`tradar-connector-*`, directly under `crates/`) only implements those traits and depends on nothing else in the workspace; code in `tradar-query-workbench` (components, `query_engine`) depends only on the `QueryDriver` trait, never on a concrete connector crate. This is what lets new databases be added without touching core logic — see the "Registry" section in `docs/architecture.md`.

Other standing principles from the design spec:

- Prefer interfaces over concrete implementations; reuse shared UI components whenever possible.
- Keyboard-first, terminal-first — every feature must work without a mouse; keep startup fast and memory usage low.
- Support large result sets efficiently — virtual scrolling/pagination, avoid loading unnecessary data into memory.
- Unit tests for core logic (`components`, `query_engine`), integration tests per driver.
- Update documentation whenever behavior changes.

- `async-trait` — enables the async `QueryDriver`/`Connector`/`Session` traits
- `sqlx` (sqlite + postgres + mysql features) — the Postgres/MySQL/SQLite connector crates are built on this

- `rdkafka` (feature `cmake-build`, binds `librdkafka`) — the Kafka connector; builds `librdkafka` from vendored source via CMake, needs `cmake`/`gcc`/`libcurl-dev` on the build machine

- `toml` — saved-connections/session/config/snippets/saved-HTTP-requests file format (`tradar-core` only)
- `directories` — platform-appropriate config path for the saved-connections/session/config files (`tradar-core` only)
- `serde` / `serde_json` — serialization
- `anyhow` — error handling
- `base64` — encodes yanked text for the OSC52 clipboard escape sequence (`tradar-core`'s `ui::yank_to_clipboard`, called from both `tradar-query-workbench` and `tradar-connector-http`)
- `arboard` (`default-features = false`, text only — no `image`/`image-data`) — reads the OS clipboard for middle-click paste (`tradar-core`'s `ui::paste_from_clipboard`); OSC52 is copy-only and has no read side a terminal can answer, hence a real clipboard library for this direction
- Dev-only: `tempfile` (driver/storage tests use real temp files, not mocks), `testcontainers-modules` (spins up real Postgres/MongoDB/Elasticsearch/Redis instances for connector tests), `testcontainers` directly via `GenericImage` (Cassandra/RabbitMQ/Kafka/HTTP — no `testcontainers-modules` support for those four)

Present in `tradar-app/Cargo.toml` but not yet used by any code: `clap`, `thiserror`, `tracing`/`tracing-subscriber`.
